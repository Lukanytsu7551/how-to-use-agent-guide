# 附录 B / 模式选择指南

不要因为模式名称听起来更复杂，就默认采用更复杂的架构。先看任务的不确定性、并行性、失败代价和运行时长，再选择足够简单的方案。

| 任务特征 | 优先考虑 | 选择理由 |
| --- | --- | --- |
| 单轮、输入输出清晰 | 单 Agent + 工具 | 结构简单，容易调试和验收 |
| 需要先拆解再执行 | Planning | 先明确步骤、依赖和停止条件 |
| 结果需要复核 | Reflection | 用独立检查发现结构或事实问题 |
| 多个步骤可以并行 | DAG | 显式表达依赖、并行和汇聚 |
| 角色之间需要动态交接 | Handoff | 保持专长边界，传递必要状态 |
| 需要探索多种候选方案 | Tree-of-Thoughts | 并行探索后再评分、剪枝和收敛 |
| 需要对立观点审查 | Debate | 让质疑成为流程的一部分 |
| 任务持续时间很长 | 持久化 Agent Loop | 保存检查点，支持恢复、暂停和接管 |
| 任务涉及高风险外部动作 | 受控工具 + 人工审批 | 将权限、确认和回滚放在系统层 |

## 一个简单的决策顺序

1. 先确认单 Agent 是否可以在可接受的时间和成本内完成。
2. 如果步骤固定，优先使用普通工作流或 DAG。
3. 如果下一步依赖运行结果，再考虑 Agent Loop。
4. 只有当角色边界能降低复杂度时，才拆成多 Agent。
5. 所有涉及写入、发送、删除或权限变更的动作，都要补充审批和回滚。
