# WorkBuddy 问题排查

WorkBuddy 没有按预期运行时，先不要连续重复同一个指令。先确认问题发生在安装、账号、任务执行还是外部工具接入，再用一个最小任务复现。这样可以把“产品问题”“网络问题”和“输入资料问题”分开处理。

本文结合 WorkBuddy 的桌面端、工作区、Skill、MCP、连接器和助理接入场景整理。产品菜单、模型额度和日志路径可能随版本变化，请以当前版本界面为准。

## 先判断问题在哪一层

| 阶段 | 常见现象 | 优先检查 |
| --- | --- | --- |
| 安装 | 安装失败、更新失败、Skill 装不上 | 系统版本、安装包来源、旧版本残留、缓存和安装目录 |
| 登录 | 登录页卡住、账号不对、额度异常 | 浏览器授权、登录账号、网络、套餐或额度状态 |
| 使用 | 任务不执行、结果不完整、终端打不开 | 工作区、权限、任务输入、模型、终端和运行模式 |
| 工具接入 | Skill、MCP、连接器、API 或助理无响应 | 配置格式、授权范围、网络连通性、服务端状态 |
| 反馈 | 自己无法定位或问题反复出现 | 版本、系统、复现步骤、脱敏日志和错误截图 |

## 使用方法

1. 先完成当前分类下的基础检查，再尝试修改设置。
2. 用空目录、短文本或一个简单指令复现，避免一次同时改变多个变量。
3. 每次只改一个设置，并记录修改前后的结果。
4. 需要求助时，提供脱敏后的版本、系统、工作区、复现步骤、错误截图和日志片段。

> 不要直接上传 API Key、Cookie、访问令牌、企业内部地址、身份证号、手机号或包含个人文件内容的完整日志。

## 一、安装与更新

### 安装包打不开或安装失败

先确认安装包来自可信的 WorkBuddy 官方入口，并检查系统版本是否满足当前版本要求。安装过程中如果出现权限、签名或文件损坏提示，可以依次尝试：

1. 重新下载当前版本安装包，避免使用中断下载的旧文件。
2. 退出正在运行的 WorkBuddy 进程，再重新执行安装。
3. macOS 检查系统是否阻止了应用打开；Windows 检查安全软件、管理员权限和安装目录权限。
4. 不要把个人项目、截图或资料放在应用安装目录中。

### 更新时提示安装目录中存在用户文件

部分桌面应用更新会覆盖旧版安装目录。若安装目录里混入了项目、下载文件或截图，更新程序可能提示风险，严重时还可能造成文件丢失。

处理方式：

1. 打开 WorkBuddy 的应用安装位置。
2. 将个人项目和任务产出移动到独立的工作区目录。
3. 只保留应用自身的程序目录，不在安装目录里保存个人文件。
4. 重新打开 WorkBuddy，从帮助或设置菜单执行检查更新。

### Skill 或扩展安装失败

安装失败常见于旧版本残留、重复安装、下载缓存损坏或 Skill 版本与当前 WorkBuddy 不匹配。

可以按这个顺序处理：

1. 在 WorkBuddy 中卸载失败的 Skill 或扩展。
2. 关闭 WorkBuddy，清理当前版本的安装缓存；优先使用“帮助 → 打开日志文件夹”定位目录，不要凭猜测删除系统文件。
3. 检查用户 Skill 目录中是否存在同名旧版本，必要时先备份再移走。
4. 重新打开 WorkBuddy，安装与当前版本匹配的版本。
5. 如果仍然失败，记录 Skill 名称、版本、安装日志和失败时间。

## 二、登录与账号

### 卡在登录界面，浏览器没有完成授权

登录窗口没有被正确拉起时，可以尝试：

1. 选择“在浏览器中打开”，重新拉起登录验证。
2. 选择“复制登录链接”，手动粘贴到默认浏览器中完成授权。
3. 检查默认浏览器是否拦截了弹窗或禁止了第三方 Cookie。
4. 完成授权后回到 WorkBuddy，等待客户端同步登录状态。
5. 如果页面已经显示完成但客户端仍未登录，退出客户端后重新打开，再用同一账号登录。

### 登录后提示额度不足或功能不可用

先确认以下几项：

- 当前登录账号是否就是购买套餐或获得权限的账号。
- 当前工作区是否切换到了正确的组织或团队。
- 模型、联网、文件处理或工具调用是否消耗独立额度。
- 是否已达到当日、当月或当前模型的使用限制。

可以退出当前账号，再通过原来的手机号、邮箱或组织账号重新登录。不要只反复刷新对话窗口，先确认账号和工作区身份。

## 三、使用与任务执行

### 任务没有开始或长时间没有结果

先把任务缩减成一个最小版本，例如“读取一个小文本并提取三条信息”。如果最小任务可以完成，再逐步增加文件、工具和输出要求。

重点检查：

1. 当前工作区是否已打开，任务需要的文件是否真的位于工作区内。
2. WorkBuddy 是否有读取目标目录、写入输出目录或执行命令的权限。
3. 当前模式是否允许执行任务、调用工具和修改文件。
4. 任务中是否同时要求了联网、读取大量文件、生成图片和导出文档，导致排查范围过大。
5. 任务是否超出模型上下文或单次运行时间限制。

### 结果不完整、格式不对或反复跑偏

把需求拆成“输入、动作、验收标准”三部分，并明确输出位置。例如：

```text
输入：读取当前工作区的 3 个 Markdown 文件。
动作：提取标题、日期和结论，去重后整理成表格。
验收：输出到 output/summary.md，保留原始文件，不得修改 source/。
```

如果仍然不稳定，先关闭不必要的 Skill、连接器或自动化任务，再逐个恢复。复杂任务应要求 WorkBuddy 先给出计划，执行后再检查文件是否真的生成。

### 终端打不开或终端状态无法复用

在 WorkBuddy 的设置中搜索 `Shell` 或 `Terminal`，确认终端集成和 Shell Integration 相关选项已启用。

如果 macOS 使用 zsh，过于复杂的主题、启动脚本或慢速插件可能让终端状态无法及时返回。可以暂时使用一个干净的 bash/zsh 配置启动 WorkBuddy，确认是否为 `~/.zshrc` 中的主题或插件导致，再逐项恢复配置。

### 如何约束 WorkBuddy 的回答语言和工作方式

将稳定规则写入 WorkBuddy 可读取的 Rules、项目说明或 Skill 中，例如：

- 默认使用中文回答，代码和命令保留原文。
- 执行删除、发送、发布或部署前必须先确认。
- 所有产出写入指定目录，不覆盖原始资料。
- 任务结束时列出实际生成的文件和未完成事项。

规则需要短、明确、可验证。不要把一次性任务要求全部写成全局规则，避免影响其他工作区。

### 工作区或历史会话找不到了

先确认是否切换到了不同的工作区、设备或远程模式。最近执行的任务可能出现在任务列表，而较早的任务只保留在工作区列表中。

如果使用远程控制、助理或小程序接入，先确认当前查看的是本机任务还是云端任务，并检查目标电脑是否在线。不要只在当前对话列表中查找。

## 四、工具接入

### 代理检测失败或出现 `ECONNREFUSED`

这通常意味着代理已配置，但代理进程没有启动、端口不可达、地址填写错误，或代理协议与客户端不兼容。

排查顺序：

1. 检查 WorkBuddy 设置中的代理地址、协议和端口。
2. 确认本机代理软件正在运行，并确认端口处于监听状态。
3. 优先使用客户端明确支持的 HTTP 代理配置。
4. 在终端用实际的 WorkBuddy 服务地址测试连通性：

```bash
curl -v https://<WorkBuddy 服务地址>
curl -x http://127.0.0.1:<代理端口> -v https://<WorkBuddy 服务地址>
```

5. 如果不需要代理，临时关闭代理后重新执行一次任务，判断问题来自代理还是服务端。

### Hosts 或 DNS 检查异常

检查本机是否存在旧的域名映射、异常 DNS 或 VPN/系统代理干扰：

- macOS/Linux：`/etc/hosts`
- Windows：`C:\Windows\System32\drivers\etc\hosts`
- macOS/Linux：`nslookup <WorkBuddy 服务域名>` 或 `dig <WorkBuddy 服务域名>`
- Windows：`nslookup <WorkBuddy 服务域名>`

删除确认错误的映射并刷新 DNS 缓存后，再重新运行网络检查。不要直接删除整份 hosts 文件。

### 服务连通性、TCP 或丢包检查失败

单项网络检查失败不一定代表 WorkBuddy 完全不可用。可以交叉判断：

| 检查项 | 可能原因 | 补充验证 |
| --- | --- | --- |
| HTTP 服务连通性 | 请求被拦截、超时、证书或代理鉴权失败 | `curl -v https://<WorkBuddy 服务地址>` |
| TCP 连接延迟 | 防火墙或企业网络阻断 443 端口 | `nc -vz <WorkBuddy 服务域名> 443` |
| 丢包率 | 链路质量差，或目标禁用了 ICMP | `ping -c 10 <WorkBuddy 服务域名>`；Windows 使用 `ping -n 10` |

如果网页和对话都能正常使用，但 Ping 显示 100% 丢包，优先判断为 ICMP 被限制，再结合 HTTP 和 TCP 结果判断，不要单凭 Ping 结论下判断。

### MCP 连接不上

先确认当前模式允许调用工具，并检查 MCP 配置：

1. 配置文件是否为合法 JSON/TOML，字段名称、逗号和引号是否正确。
2. 服务命令或路径是否真实存在，依赖是否已经安装。
3. 环境变量和 API Key 是否在 WorkBuddy 进程中可见。
4. 服务名称不要使用当前配置格式不支持的空格或特殊字符。
5. 重启 MCP 服务和 WorkBuddy，再观察连接日志中的第一条错误。

不要把完整的密钥配置贴到反馈中，只保留字段名和脱敏后的错误信息。

### Skill、连接器或助理接入后没有响应

按接入类型检查：

- Skill：名称、版本、安装位置和所需依赖是否匹配。
- 连接器：是否完成账号授权，授权范围是否包含当前任务需要的数据。
- API：Base URL、模型名、密钥、超时和模型能力是否匹配。
- 助理/小程序：桌面端是否保持运行，目标电脑是否在线，WebSocket 或 URL 回调是否可达。
- 企业微信、飞书、钉钉：机器人是否仍处于启用状态，回调地址、Token 和加密配置是否一致。

接入问题优先使用一个最小动作验证，例如只读取一条消息或调用一个无副作用的接口，确认连接成功后再执行写入、发送或发布操作。

### 自定义模型调用失败

先用 WorkBuddy 的 Auto 或默认模型完成一个简单对话，再单独验证自定义模型。重点检查：

1. Base URL 是否填写到 API 要求的路径层级。
2. 模型名称是否为服务端实际支持的名称。
3. API Key 是否过期，账号是否还有额度。
4. 模型是否支持图片输入、工具调用、流式输出或思考模式。
5. 请求是否超过模型上下文长度或单次输出限制。

## 五、反馈与日志

### 如何查看本地日志

优先使用 WorkBuddy 菜单中的“帮助 → 打开日志文件夹”，获取与故障发生时间接近的日志压缩包。不同系统和版本的日志目录可能不同，菜单入口比手动猜路径更可靠。

如果需要手动查找，可以在用户目录下搜索名称包含 `WorkBuddy`、`logs` 或 `log` 的目录；不要上传整个用户目录。

### 提交问题前准备什么

建议按下面模板整理，先脱敏再提交：

```text
问题标题：一句话描述现象
WorkBuddy 版本：
系统与版本：macOS / Windows / Linux + 版本号
工作区：本机 / 云端 / 助理或小程序
发生时间：
复现步骤：
预期结果：
实际结果：
是否稳定复现：是 / 否
已尝试操作：
错误信息或日志片段：
相关 Skill、MCP、连接器或模型：
```

反馈中可以附上错误截图，但请先遮挡账号、手机号、邮箱、文件路径、密钥、Cookie 和企业内部信息。若问题与版本变化有关，同时附上当前版本和最近一次正常工作的版本。

### 常见错误码怎么定位

如果错误码来自网络检查或服务响应，先把它和具体检查项对应起来：

- 连通性类错误：优先看 HTTP 服务连通性和 TCP 443 端口。
- 超时类错误：先重试，再检查丢包、代理和任务上下文长度。
- 代理类错误：检查协议、地址、端口和代理进程是否启动。
- 工具类错误：检查 Skill/MCP/连接器的配置、权限和依赖，不要只重试对话。

## 仍然无法解决怎么办

如果这里没有对应记录，建议按这个顺序继续：

1. 查看 [WorkBuddy 官方文档](https://www.codebuddy.cn/docs/workbuddy/Overview) 和当前版本的帮助、更新说明。
2. 记录脱敏日志、版本、系统、复现步骤和最小复现任务。
3. 让 AI 按“现象 → 可能原因 → 验证步骤 → 修复方案”分析日志。
4. 在官方支持渠道或团队内部反馈，并附上整理好的问题模板。
